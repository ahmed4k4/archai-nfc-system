# ملاحظات الأمان — v6.5

- كل حساب إداري يحتاج مستند `users/{uid}` نشطًا ودورًا معتمدًا.
- عزل مدير البراند يعتمد على `brandId` داخل قواعد Firestore، وليس على إخفاء عناصر الواجهة.
- إنشاء العميل العام لا يتطلب حسابًا، لكنه يتطلب token موجودًا ونشطًا، وفرعًا وبراندًا نشطين ومتطابقين، ومصدرًا صحيحًا QR أو NFC.
- يسمح للعميل بقراءة مستند token بمعرفه فقط؛ سرد مجموعة `branchTokens` ممنوع.
- قواعد إنشاء العميل تشترط موافقة `consent: true`، وإصدار `consentVersion: '1.0'`، ووقتًا يساوي `request.time` عبر Firestore `serverTimestamp()`.
- مدير البراند لا ينشئ أو يعدل مستخدمين ولا يفتح صلاحية الحقول، ولا يغيّر هوية الفرع أو token أو مصدره.
- صلاحية تعديل الحقول محدودة 30 دقيقة، ويُغلق مستند البراند بعد اكتمال تحديث كل tokens والحفظ.
- تحديث tokens يتم في دفعات لا تتجاوز 450 عملية؛ في حالة فشل دفعة تبقى الصلاحية مفتوحة حتى انتهاء مدتها أو إعادة المحاولة.
- صورة البراند التي تظهر للعملاء تمر عبر `brandImage` في وثيقة token العامة، وتظل ملفات الصور ثابتة في Hosting. لا يُسمح بمسارات خارج `assets/brands/` من واجهة لوحة الإدارة.
- ملف Excel يُنشأ محليًا في متصفح المدير ولا يُرفع إلى خدمة خارجية، مع حماية أساسية من Excel formula injection.
- لا يُسمح بتحديث بيانات العملاء بعد إنشائها. الحذف متاح فقط لمدير النظام أو مدير البراند المرتبط بسجل العميل، وتمنع القواعد أي حذف من الزائر العام.

## قبل الإنتاج
1. اختبر قواعد Firestore في Firebase Emulator Suite أو مشروع staging. لا تعتبر التحليل الساكن بديلًا عن اختبار القواعد.
2. انشر الاستضافة والقواعد في الإصدار نفسه؛ قواعد الإصدار الحالي تشترط حقول الموافقة الجديدة.
3. اختبر صلاحيات Super Admin وBrand Admin والتسجيل العام بحسابات منفصلة.
4. فعّل App Check بعد إعداد مزود مناسب واختباره.
5. وفر سياسة خصوصية حقيقية ومحددة، وحدد مدة الاحتفاظ وآلية التعامل مع طلبات حذف البيانات، مع الانتباه إلى أن حذف السجل من الواجهة نهائي.
6. فعّل مراقبة الاستهلاك والتنبيهات وخطة نسخ احتياطية.

## حدود معلومة
- QR/NFC التقليديان رابطان ثابتان يمكن نسخهما؛ لا يمكن منع الاستنساخ دون NFC تشفيري وقارئ يتحقق من التوقيع.
- يجب تثبيت الدومين ومسار `scan.html` قبل الطباعة؛ تغيير الدومين لا يغير الروابط القديمة تلقائيًا.
- QR وExcel يحتاجان تنزيل مكتباتهما من CDN عند الاستخدام.
- لم يتم تنفيذ اختبار حي مع Firebase أو Firebase Emulator في بيئة التجهيز؛ يجب إتمام قائمة اختبار ما قبل الإنتاج.


## استثناء HTTP للتطوير المحلي (v5.2)
يسمح النظام باستخدام HTTP فقط عند التطوير على loopback (`localhost` أو `127.0.0.1` أو `::1`) وبشرط تطابق أصل `PUBLIC_APP_URL` مع أصل الصفحة المفتوحة. لا يسمح بعناوين LAN أو الإنترنت عبر HTTP. لا تستخدم روابط localhost في بطاقات العملاء؛ استبدلها بدومين HTTPS نهائي قبل إنشاء فروع الإنتاج.

- v5.3: لوحة الإدارة لا تعتبر فشل استعلام العملاء سببًا لإخفاء البراندات والفروع والحقول؛ يتم إظهار خطأ العملاء بشكل منفصل.
- فهرس العملاء المركب محدد بنطاق COLLECTION ويجب نشره عبر Firebase CLI قبل استعلام مدير البراند المرتب حسب createdAt.
- v5.3: إنشاء سجل العميل يشترط أن يكون `createdAt` و`consentAt` مساويين لوقت الطلب (`request.time`) لمنع التلاعب بتاريخ التسجيل.


## إضافات الصلاحيات في v6.3

- لا يوجد إذن لتحديث سجل العميل بعد إنشائه.
- الحذف مسموح فقط لمدير النظام أو مدير البراند المرتبط بـ `brandId` الخاص بالسجل.
- بيانات صور البراند التي تظهر للعامة تُمرر من وثيقة `branchTokens`، بينما اختيار الصورة وتحديثها محصور في مدير النظام.
- يجب نشر قواعد Firestore الجديدة قبل استخدام زر حذف العملاء.


## ضوابط الحذف المتسلسل في v6.3

- قبل الحذف يتم تعطيل البراند/الفرع ورموز QR/NFC حتى لا تقبل روابط التسجيل طلبات جديدة أثناء تنظيف البيانات.
- عمليات الحذف تُنفذ على دفعات أصغر من حد Firestore الأقصى، مع إبقاء مستند البراند أو الفرع حتى نهاية التنظيف قدر الإمكان لتسهيل إعادة المحاولة بعد أي فشل جزئي.
- لا تسمح القواعد بحذف البراند إلا لمدير النظام. مدير البراند يستطيع حذف الفروع والرموز والعملاء التابعة لبراندِه فقط.
- لا يستطيع Firebase Client SDK حذف حساب Auth لمستخدم آخر. عند حذف براند يتم ضبط `users/{uid}.active = false`، ويظل حذف حساب Authentication نفسه إجراءً يدويًا من Firebase Console أو Backend موثوق.
- صفحة التسجيل العامة لا تحتوي على شعار Archai أو favicon ثابت له؛ إن وُجد شعار براند صالح يظهر وحده ويُستخدم كأيقونة للصفحة، وإلا يُخفى موضع الشعار.


## تقارير Excel في v6.5

- يُنشأ ملف Excel محليًا في متصفح المدير ولا يُرفع إلى خدمة خارجية.
- يفصل التصدير كل فرع في ورقة مستقلة ويطابق سجلات العملاء بواسطة `brandId` و`branchId` معًا.
- عند وجود سجل لا يطابق أي فرع معروف ضمن نطاق التصدير، يتوقف التصدير برسالة بدل جمعه داخل ورقة غير صحيحة.


## تقارير Excel في v6.5

- يتم توليد ملف Excel محليًا في متصفح المدير ولا يُرفع إلى خدمة خارجية.
- يحتوي الملف على ملخص الفروع وملخص البراندات وورقة مستقلة لكل فرع.
- مطابقة سجلات العملاء داخل أوراق الفروع تعتمد على `brandId` و`branchId` معًا، مع تعريفات حقول البراند نفسه فقط.
- التصدير يوقف العملية إذا اكتشف سجلًا لا يتطابق مع فرع وبراند معروفين بدل تسريبه إلى ورقة أخرى.
- يستخدم التصدير `xlsx-js-style` من jsDelivr لدعم تنسيق الخلايا؛ يحتاج اتصالًا بالإنترنت عند أول تحميل للمكتبة.
- مدير البراند لا يظهر له فلتر البراند، ويُفرض نطاق `profile.brandId` على بياناته وتصديره. إخفاء الفلتر ليس بديلًا عن قواعد Firestore، التي تظل مصدر العزل الفعلي.


## حدود تصدير البيانات حسب الدور (v6.6)

- يحدد كود التصدير نطاق البراندات قبل بناء Workbook: `super_admin` فقط يرى جميع البراندات، و`brand_admin` يقتصر على `profile.brandId`.
- لا يعتمد تقرير مدير البراند على إخفاء ورقة الإدارة؛ لا يتم إنشاؤها أصلًا، كما لا تدخل بيانات البراندات الأخرى في أي ورقة أو بيانات وصفية للمصنف.
- يتم التحقق من تطابق `brandId` و`branchId` قبل إسناد العملاء إلى أوراق الفروع. يتم إيقاف التصدير عند وجود سجل يتيم أو فرع لا يتبع براندًا معروفًا بدل إسقاطه أو خلطه.
- التصدير محلي في المتصفح ولا يرسل ملف Excel إلى خدمة خارجية. قواعد Firestore المنشورة تظل مصدر التحكم الفعلي في ما يمكن للحساب قراءته.
