# تقرير مراجعة الإصدار 6.6

**المشروع:** Archai Branch System  
**المراجعة:** فحص ثابت + محاكاة متصفح Chromium + فحص الاستجابة للشاشات  
**حالة ملفات الإصدار:** اجتازت الفحوصات المحلية الموضحة أدناه. لم يتم نشرها على مشروع Firebase الحقيقي للمستخدم.

## 1. معالجة رسالة فهرس Firestore

تم استبدال استعلام العملاء السابق الذي كان يجمع بين شرط `brandId` وترتيب Firestore حسب `createdAt`.

الاستعلام الحالي:

- مدير النظام: قراءة مجموعة `customers` التي تسمح له قواعد Firestore بقراءتها.
- مدير البراند: شرط مساواة واحد فقط `brandId == profile.brandId`.
- ترتيب النتائج حسب `createdAt` تنازليًا داخل المتصفح بعد تحميل المستندات.
- لا يوجد `orderBy(createdAt)` في استعلام العملاء، ولا يوجد فهرس مركّب مطلوب لهذا المسار.
- ملف `firestore.indexes.json` لا يحتوي على فهرس مركّب خاص بالعملاء.

تم كذلك فصل تحميل العملاء عن تحميل البراندات والفروع؛ ففشل تحميل العملاء لا يمنع ظهور بقية لوحة الإدارة أو معاينة الحقول.

**ملاحظة أداء:** هذا التنفيذ يحمّل كل سجلات العملاء المصرح بها إلى المتصفح، ثم يطبق الترتيب والبحث والفلاتر محليًا. هذا يلغي طلب الفهرس المركّب ويعطي أعدادًا وتصديرًا كاملين في حجم البيانات الحالي، لكنه يزيد عدد القراءات والذاكرة مع نمو قاعدة العملاء. عند الوصول إلى أحجام كبيرة يجب نقل العدّ والتقارير إلى Backend/Cloud Functions وإضافة Pagination.

## 2. إدارة البراندات وتفاصيلها

- بطاقة كل براند تعرض الاسم والبريد والحالة وعدد الفروع وعدد العملاء وعدد الحقول.
- نافذة التفاصيل تعرض بيانات البراند والحالة وتاريخ الإنشاء وحقول التسجيل والفروع التابعة وعدد المسجلين في كل فرع.
- مدير النظام يستطيع فتح محرر حقول أي براند مباشرة من بطاقة البراند أو نافذة تفاصيله.
- يستطيع مدير النظام أيضًا منح مدير البراند صلاحية تعديل مؤقتة لمدة 30 دقيقة.
- مدير البراند يرى معاينة حقول برانده فقط، ولا يستطيع فتح المحرر قبل منح الصلاحية.
- بعد نجاح حفظ مدير البراند، يتم إغلاق الصلاحية تلقائيًا.

## 3. الفروع وإحصاء المسجلين

- نموذج إنشاء الفرع لا يحتوي على عنوان أو منطقة أو حقول إضافية.
- مدير النظام يختار البراند ويكتب اسم الفرع فقط.
- مدير البراند يكتب اسم الفرع فقط؛ لا يظهر له محدد براند ولا يمكنه اختيار براند آخر.
- يتم إنشاء روابط QR وNFC ثابتة للفرع عند إنشائه.
- بطاقة الفرع تعرض عدد سجلات العملاء المرتبطة بـ `branchId` الخاص به، ويظهر العدد نفسه في تفاصيل البراند.
- إيقاف الفرع لا يبدل الرموز أو الروابط.

## 4. العملاء والتسجيل والتصدير

- العملاء يعرضون في بطاقات RTL بدل جدول عريض، مع الاسم والهاتف والبراند والفرع والمنتج والمصدر وتاريخ التسجيل والحقول المخصصة.
- السجلات مرتبة من الأحدث إلى الأقدم.
- تم اختبار البحث النصي، وعدد النتائج، وفلترة السجلات.
- في الإصدار السابق تم اختبار مسار تجهيز بيانات Excel بمحاكاة مكتبة SheetJS. في الإصدار 6.5 يستخدم التصدير مكتبة SheetJS CE 0.20.3 الموجودة في المشروع لإنشاء أوراق متعددة مع عناوين واضحة وأحجام أعمدة وفلاتر؛ لم يمكن تنزيل CDN أو فتح ملف مولّد فعليًا في بيئة البناء الحالية.
- نموذج التسجيل يقرأ إعدادات الحقول من رمز QR/NFC.
- تم اختبار الحقول الديناميكية والإلزامية، والتحقق من الاسم والهاتف، ورفض الإرسال قبل الموافقة، ثم تكوين سجل العميل الصحيح بعد الموافقة.

## 5. الأمان والصلاحيات

- تم الحفاظ على قواعد فصل بيانات البراندات حسب `brandId`.
- لا يستطيع مدير البراند سرد أو قراءة بيانات براند آخر من خلال الواجهة.
- لا يستطيع مدير البراند تعديل الحقول دون صلاحية فعالة من مدير النظام.
- رمز الفرع لا يسمح بسرد مجموعة `branchTokens`.
- لا تسمح القواعد بتحديث سجلات العملاء بعد التسجيل.
- تسمح القواعد بالحذف لمدير النظام أو لمدير البراند صاحب سجل العميل فقط؛ لا يمكن لزائر QR/NFC حذف السجل.
- صور البراند لا تُقبل من الواجهة إلا إذا كانت مسارات ملفات ثابتة ضمن `assets/brands/`، ويتم إرسال المسار في وثيقة رمز QR/NFC للعرض العام.
- تم حذف حقل `location` من نموذج إنشاء الفرع ومن قائمة الحقول المسموح بها عند الإنشاء.
- مراجعة ملفات القواعد كانت ساكنة؛ لم يتم تشغيل Firebase Emulator أو نشر القواعد إلى مشروع حي.

## 8. الفحوصات الثابتة

- جميع ملفات JavaScript اجتازت `node --check`.
- إعدادات JSON اجتازت التحليل.
- HTML وملفات CSS وروابط الموارد المحلية اجتازت الفحص.
- لا يوجد استعلام عملاء يجمع `brandId` مع `orderBy(createdAt)`.

- تم فحص سلامة ملف ZIP النهائي باستخدام `unzip -t` بعد التغليف.

## 9. ما لم يمكن اختباره

لم تتوفر مفاتيح Firebase Web App الخاصة بالمستخدم ولا جلسة دخول إلى مشروع `archai-nfc-system`، ولذلك لم يتم تنفيذ قراءة/كتابة حقيقية على Firestore، أو التحقق من قواعد Firebase المنشورة، أو اختبار إنشاء حساب Auth حقيقي، أو تحميل مكتبات QR وXLSX من الإنترنت. الاختبارات الوظيفية أعلاه تمت بمحاكاة Firestore/Auth داخل Chromium، ولا تُعد بديلًا عن اختبار المشروع بعد وضع إعدادات Firebase الفعلية.

بعد نسخ إعدادات Firebase الحقيقية إلى `js/firebase.js`، اضبط `PUBLIC_APP_URL` إلى رابط HTTPS النهائي، ثم انشر القواعد والاستضافة يدويًا من Terminal:

```bash
firebase use archai-nfc-system
firebase deploy --only firestore:rules,hosting
```

لا يتطلب الإصدار فهرس عملاء مركّبًا. لا يوجد ملف BAT أو مجلد config فارغ في حزمة الإصدار؛ إعدادات Firebase موزعة في `js/firebase.js` و`firebase.json` و`.firebaserc`. لا تنشئ فروعًا حقيقية برابط `127.0.0.1` لأن الروابط تُحفظ بشكل دائم.


## 10. إضافات الإصدار 6.2

- إضافة كتالوج صور محلي في `assets/brands/manifest.json` وصورة SVG تجريبية.
- إضافة زر اختيار صورة لكل براند في بطاقته وتفاصيله، مع معاينة قبل الحفظ.
- مزامنة مسار الصورة مع مستندات رموز QR/NFC التابعة للبراند بحيث يرى العميل صورة البراند في صفحة التسجيل، دون تبديل الرابط أو الرمز.
- ظهور صورة البراند في شريط مدير البراند، وبطاقات البراندات وتفاصيلها.
- إضافة نافذة تفاصيل للعميل تعمل من البطاقة أو زر التفاصيل، مع جميع الحقول القياسية والمخصصة.
- إضافة حذف سجل العميل بعد تأكيد صريح، مع إزالة السجل من الواجهة وإعادة حساب الإحصاءات.
- إضافة Pagination مرقم يعرض 12 سجلًا في الصفحة، ويدعم السابق/التالي، ويعيد الصفحة الأولى عند تغيير البحث أو الفلاتر.

**تنبيه الاختبار:** لم يتم الاتصال بمشروع Firebase الحقيقي أو تشغيل Firebase Emulator في هذه البيئة. يجب نشر `firestore.rules` الجديدة مع تحديث ملفات Hosting، ثم اختبار الحذف فعليًا بحساب مدير النظام ومدير البراند. لقطات Chromium الحالية موروثة من مراجعة الإصدار السابق؛ لم أُنشئ لقطات جديدة للتغييرات الأخيرة.


## 11. إضافات الإصدار 6.3

- إضافة حذف الفرع لمدير النظام ومدير البراند داخل حدود البراند المرتبط به.
- حذف الفرع يشمل تعطيل الفرع ورمزي QR/NFC أولًا، ثم حذف العملاء والرموز والفرع على دفعات Firestore.
- إضافة حذف البراند لمدير النظام فقط، مع حذف الفروع والعملاء والرموز المرتبطة به وتعطيل ملفات مديري البراند في مجموعة `users`.
- ملفات Firebase Authentication لمديري البراند لا يمكن حذفها من SDK العميل؛ يتم تعطيل ملف Firestore الخاص بها لمنع دخول لوحة النظام، ويتطلب حذف حساب Auth نهائيًا إجراءً يدويًا من Firebase Console أو Backend موثوق.
- أزيل شعار Archai من صفحة التسجيل العامة ومن الأيقونة الثابتة للصفحة. يتم إظهار صورة البراند فقط، وتُستخدم كأيقونة تبويب عند توفرها؛ لا يظهر شعار بديل عند عدم تعيين صورة.
- قواعد Firestore تسمح بحذف الفرع ورموز QR/NFC بواسطة مدير النظام أو مدير البراند صاحب البراند فقط. حذف البراند ما زال مقتصرًا على مدير النظام.

**حدود التحقق:** تم فحص بنية الكود وقواعد Firestore وفحوص الصياغة محليًا. لم تتوفر بيانات Firebase الحقيقية أو Emulator في هذه البيئة، لذلك يجب نشر القواعد واختبار سيناريو حذف فرع بحساب مدير براند، وحذف براند بحساب مدير النظام قبل استخدامه في الإنتاج.


## 12. إضافات الإصدار 6.5

- تصدير Excel أصبح متعدد الأوراق باستخدام SheetJS CE 0.20.3: ورقة مستقلة لكل فرع في نطاق المستخدم وفلاتر صفحة العملاء، مع إظهار البراند والفرع والعدد أعلى كل ورقة.
- سجلات كل ورقة تُطابق `brandId` و`branchId` معًا، والحقول الإضافية مأخوذة من إعدادات البراند نفسه وسجلات الفرع نفسه.

- فحص `node --check` لملفات JavaScript بعد التعديل اجتاز بنجاح.
- راجع النشر: تم تعديل HTML وJavaScript وCSS وملفات التوثيق فقط؛ لم تتغير قواعد Firestore أو بنية البيانات في هذا الإصدار.


## 13. إضافات الإصدار 6.5

- أضيفت ورقة «ملخص الفروع» في بداية ملف Excel، وتتضمن البراند والفرع والحالة وعدد العملاء وتوفر QR/NFC وتاريخ الإنشاء ومعرّف الفرع.
- أضيفت ورقة «ملخص البراندات» بإحصاءات الفروع النشطة والمتوقفة وعدد العملاء والبريد ومسار صورة البراند.
- بعد الملخصات، تُنشأ ورقة مستقلة لكل فرع حتى إن لم يكن به عملاء.
- يتم تجميع العميل داخل ورقة الفرع فقط إذا تطابق `brandId` و`branchId` معًا. تُستخدم حقول البراند نفسه، وتُرفض عملية التصدير إذا ظهرت سجلات غير مرتبطة بفرع/براند معروفين ضمن نتائج التصدير.
- أضيفت تنسيقات عناوين ورؤوس وجداول وصفوف متبادلة الألوان وحدود وأحجام أعمدة وتواريخ وفلاتر وتجميد رؤوس. يعتمد التنسيق على `xlsx-js-style` من jsDelivr.
- أصبح محدد البراند في صفحة العملاء مخفيًا لمدير البراند، ويُفرض `profile.brandId` في التصفية والتصدير. مدير النظام يحتفظ بفلتر البراند في صفحة العملاء.
- فلتر صفحة الفروع لمدير النظام موجود مستقلًا عن فلتر العملاء.

### حدود الاختبار

- اجتاز JavaScript فحص `node --check`، وملفات JSON فحص التحليل، وفحص ZIP.
- لم تتوفر المكتبة الخارجية `xlsx-js-style` داخل بيئة البناء، لذلك لم يتم توليد ملف XLSX فعلي أو فتحه في Excel/LibreOffice. يجب اختبار تنزيل الملف بعد النشر مع بيانات تجريبية.
- لم يتم الاتصال بمشروع Firebase الحقيقي أو Emulator؛ لا توجد تغييرات في قواعد Firestore أو بنية البيانات في هذا الإصدار.

- التصدير لا يتأثر ببحث أو فلاتر الشاشة: مدير النظام يحصل على جميع البراندات والفروع، ومدير البراند يحصل على كامل بيانات برانده فقط.


## 13. فصل تقارير Excel حسب الدور (الإصدار 6.6)

- تم فصل بناء المصنف إلى مسارين: `super_admin` و`brand_admin`، مع رفض أي دور آخر.
- تقرير مدير البراند يختار البراند المطابق لـ `profile.brandId` فقط قبل تجهيز البيانات. يحتوي على بيانات البراند نفسه وحقول نموذجه وفروعه وأوراق عملائه. اسم الملف وخصائص المصنف (Author وCompany) باسم البراند، ولا تُنشأ ورقة ملخص لجميع البراندات في تقريره.
- تقرير مدير النظام يستخدم جميع البراندات والفروع والعملاء المصرح بها، واسم الملف `Archai-Complete-Report-YYYY-MM-DD.xlsx` وخصائص المصنف باسم Archai. يتضمن ملخصًا عامًا، وملخص كل الفروع، وملخص كل البراندات حتى البراندات بلا فروع، وورقة مستقلة لكل فرع.
- أصبح ملخص البراندات الإداري يتضمن المعرّف والحالة والبريد ومسار الشعار وتاريخ الإنشاء وعدد الفروع والعملاء وحقول نموذج التسجيل.
- ما زالت مطابقة كل سجل عميل تتطلب `brandId` و`branchId` الصحيحين. كما يوقف التصدير الشامل إذا وجد فرعًا لا يتبع براندًا معروفًا أو عميلًا لا يتبع فرعًا معروفًا؛ لا يتم إسقاط البيانات غير المتطابقة بصمت.
- اجتاز `node --check` بعد التعديل. تم اختبار منطق إنشاء المصنف ببيانات تجريبية باستخدام mock لـ SheetJS، بما في ذلك التحقق من اسم الملف وخصائص المصنف وأسماء الأوراق وعدم ظهور بيانات البراند الثاني في تقرير مدير البراند. لم يتوفر تحميل `xlsx-js-style` من CDN، لذلك لم يتم فتح XLSX فعلي في Excel/LibreOffice.
- لم يتم الاتصال بمشروع Firebase الحقيقي أو Emulator؛ لا توجد تغييرات في قواعد Firestore أو بنية البيانات.


## 14. فلتر التاريخ في صفحة العملاء (الإصدار 6.7)

- إضافة منتقي تاريخ «من» و«إلى» باستخدام `input[type=date]` لفتح تقويم النظام واختيار الشهر واليوم والسنة.
- إضافة زر «اليوم» وزر مسح مستقل لنطاق التاريخ.
- اختبار منطق حدود التاريخ محليًا: تاريخ البداية شامل من 00:00 بالتوقيت المحلي، وتاريخ النهاية شامل عبر استخدام بداية اليوم التالي كحد حصري.
- يسمح بمدخل بداية فقط أو نهاية فقط أو الاثنين معًا؛ نطاق البداية بعد النهاية لا يُطبق.
- دمج التاريخ مع البحث وفلتر البراند والفرع مع إبقاء pagination متزامنًا.
- تضمين نطاق التاريخ الحالي في تصدير Excel دون تجاوز نطاق صلاحيات المستخدم.
- لا توجد تغييرات Firestore أو migrations أو فهارس مطلوبة.
- فحص `node --check js/app.js` ناجح، وتحليل ملفات JSON ناجح.

**حدود الاختبار:** لم يتم الاتصال بمشروع Firebase الحقيقي. منتقي التاريخ يعتمد واجهة المتصفح الأصلية وقد يختلف شكل التقويم قليلًا بين Chrome وEdge وSafari، مع بقاء الوظيفة نفسها. يلزم تجربة التفاعل على أجهزة فعلية قبل الإنتاج.


## 15. تحسين واجهة فلاتر العملاء (الإصدار 6.8)

- إعادة بناء تخطيط فلاتر العملاء بشبكة responsive على الشاشات الواسعة والمتوسطة والموبايل.
- تحسين مظهر وحدة التاريخ، حالات التركيز والتحويم، وضوح الحقول، وحجم أهداف اللمس.
- إظهار حالة تفعيل فلتر التاريخ وتعطيل زر المسح عند عدم وجود قيمة.
- إضافة حالة مرئية عند إدخال نطاق تاريخ غير صحيح دون تغيير منطق التصفية السابق.
- لا توجد تغييرات على Firestore أو قواعد الصلاحيات أو الفهارس.
- تم فحص JavaScript وJSON وسلامة ملف ZIP بعد التعديل.

**حدود الاختبار:** لم يتم تشغيل جلسة Firebase حقيقية أو اختبار الواجهة على أجهزة فعلية في هذا التحديث. منتقي التاريخ الأصلي يظل تابعًا لنظام التشغيل والمتصفح.
